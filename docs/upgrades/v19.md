# Upgrade to Umbraco 19

From `18.0.0` (Umbraco.Cms and Umbraco.Forms floor `[18.0.0, 19.0.0)`, `@umbraco-cms/backoffice` 18.0.0) to `19.0.0-rc1` (tag `release-19.0.0-rc1`).
Branch `v19/dev`, cut from `main-v18` at `ed5a0e6`.

**Targets CMS release:** `release-19.0.0-rc1`, with Umbraco.Forms `19.0.0-rc1` and Umbraco.Cms.Integrations.Automation.Zapier `7.0.0-rc1`. While this is a pre-release, the packages ship as pre-releases too: Crm.Hubspot `10.0.0-rc1`, Crm.ActiveCampaign `8.0.0-rc1` and Automation.Zapier `9.0.0-rc1`.

**In scope:** Crm.Hubspot (with Crm.Hubspot.Tests), Crm.ActiveCampaign, Automation.Zapier (added 17-11-2026, once its blocker cleared), and the test site. Cms.Integrations.OAuthProxy is a separate web app and stays out of scope.

## Follow-ups

- ActiveCampaign custom-field paging has no committed test (there is no ActiveCampaign test project). The seven scenarios used to check it are in a scratch harness only. ActiveCampaign rate limits are not handled: a 429 on any page fails the whole list with a 502.
- Replace the `property-value-change` event with `UmbChangeEvent` before Umbraco 20 (deprecated since 18, removal in 20.0.0): HubSpot `hubspot-mapping.property-editor.ts:172,184,192,200`; ActiveCampaign `account-property-editor.element.ts:44`, `contact-mapping-property-editor.element.ts:87,103`, `custom-mapping-property-editor.element.ts:90,110`.
- ActiveCampaign workflow swallows exceptions and returns `Failed` (`ActiveCampaignContactsWorkflow.cs:115-120`); Forms 18.1+ lets workflows set `context.Exception` so the failure shows in the entry's audit.
- Drop the unused, deprecated `@hey-api/client-fetch` dev dependency from both clients (bundled into `@hey-api/openapi-ts` since 0.73).
- All four editors read the form id from `window.location.pathname.split("/")[7]` (HubSpot `:72`, ActiveCampaign contact and custom mapping `:60`). Fragile across backoffice route changes; the smoke checks it still works on 19.
- The `generate:api` scripts call `openapi-ts.config.ts`, but the files in the repo are `openapi-ts.config.js`.
- `npm run lint` lints nothing in either client ("No files matching the pattern 'src'", ESLint 8.57.1). Already broken on 18.
- Both entry points configure the API client in a `consumeContext` callback; the CMS extension template uses `await host.getContext(UMB_AUTH_CONTEXT)` in an async `onInit`, which guarantees the client is configured before a lazily loaded element sends a request.
- HubSpot's mapping table delete button uses `formProviderWorkflows_delete` (`hubspot-mapping.property-editor.ts:285`), which neither HubSpot's dictionary nor Umbraco Forms 18.0.0 defines. Needs a new key or Umbraco's `general_delete`; on v17 and v18 too.
- The test site's `Program.cs` never loads `appsettings.Local.json`, so the integration settings, API keys and Forms licence kept there are ignored. The smoke runs pass the file in as environment variables instead.
- `ContactService.Get` puts the submitter's email into the query string without URL-encoding it, so an address with `+` or `&` isn't found. Already so on 17 and 18.
- `ActiveCampaignContactsWorkflow` calls `CreateAssociation` without awaiting it, so a failed account link only shows as a log warning. `CreateOrUpdate` doesn't log the status code of a failed request.
- The ActiveCampaign not-configured notice is plain text. Backoffice UX guidance is an inline line with an info icon.
- Both clients' `openapi-ts.config.js` use `asClass` and `classNameBuilder`, which `@hey-api/openapi-ts` 0.99 deprecates in favour of `operations: { strategy, containerName }`. Move over in a separate change and check the generated output is unchanged.
- Both clients resolve `@umbraco-cms/backoffice` from MyGet through their `.npmrc` (as on 18). 19.0.0-rc1 is byte-identical on npmjs; decide whether to keep MyGet for pre-releases or point the scope back at npmjs, which also gives the lockfile a SHA-512 hash.
- `npm install` reports 18 vulnerabilities (2 moderate, 16 high) in each client's dev tooling; review with `dependency-review`.
- On 19 a site restart logged the backoffice user out; on 18 the session survived a restart. Probably the new cookie auth and how this dev site stores its data protection keys; not checked further.
- A one-step `dotnet pack` on a clean tree produces packages without client assets: the csproj's `Content Include="wwwroot\**"` is evaluated before the client build writes `wwwroot`. CI works because it builds and packs in separate steps. Already so on 18.
- Both package pipelines restore with `restoreSolution: '$(solution)'`, but no `solution` variable is defined (`azure-pipeline - Crm.Hubspot.yml:30-35`, same in ActiveCampaign).
- `Testsite.V19/Directory.Packages.props` pins `Umbraco.Cms.DevelopmentMode.Backoffice`, which no project references.
- The mapping editors' `uui-select` (and one `uui-input`) have no label: the console logs `UUI-SELECT needs a label` once per select.
- A HubSpot workflow saved with no field mappings throws `JsonException` on every submission (`HubspotWorkflow.cs:38` parses the empty value). The same line is on `main-v17` and `main-v18`. Seen in the Zapier smoke, because the test site's Contact form has such a workflow.
- Automation.Zapier's OpenAPI document declares backoffice authentication (`ZapierFormsComposer.cs:43`), but its endpoints check the `X-APIKEY` or `X-USERNAME`/`X-PASSWORD` headers instead.
- Not smoke-tested for Zapier: username and password authentication (it needs a backoffice password; the CMS user manager code it calls is unchanged between 18 and 19), and a call from a browser signed in to the backoffice.
- Cms Zapier bugs, all already in Cms Zapier 6.0.0. The first two are filed as umbraco/Umbraco.Integrations.Issues#38 and #39; the third isn't filed, because an access-check gap goes through responsible disclosure. Paths are under `src/Umbraco.Cms.Integrations.Automation.Zapier/` on that repo's `v19/dev`:
  - Cms Zapier's `UserValidationService` declares `_userService` (`Services/UserValidationService.cs:10`) but its constructor never assigns it, so with the CMS `UserGroupAlias` set, username and password authentication throws a NullReferenceException at `:73`.
  - The subscription table is unique on (EntityId, Type) (`Migrations/ZapierMigration.cs:53`), so subscribing a second Zap to the same form logs a SQL error and returns `false`.
  - `check-form-extension` (`Api/Management/Controllers/CheckFormExtensionController.cs:20-22`) skips the API key check the other endpoints make. It only returns whether Umbraco Forms is installed (a boolean).
